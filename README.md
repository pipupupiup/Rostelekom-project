# ADO — Adaptive Dispatch Optimizer

**Умная диспетчеризация выездных бригад.** Веб-сервис, который распределяет наряды между выездными
сотрудниками, строит маршруты на смену, перестраивает план в реальном времени по событиям дня и
заранее предупреждает диспетчера о риске опоздания.

Кейс ПАО «Ростелеком» (УрТИСИ). Публичный API — строго по спецификации организаторов
[`spec/api_spec.yaml`](spec/api_spec.yaml): порт `8080`, префикс `/api/v1`.

> Все цифры и скриншоты в этом файле получены на **синтетических** данных (`ado.synthetic`):
> данные организаторов команде не передавались. Прогон на них — одна команда, см.
> [«Свои данные»](#загрузка-своих-данных).

## Что умеет

**Планирование смены**
- Назначает наряды сотрудникам с учётом допусков (профиль ЛТП-3 / инсталляция, технология
  PON/FTTB/xDSL/DOCSIS, работы на высоте), смены, обеденного перерыва, слота клиента, контрольного
  срока и оборудования в «рюкзаке».
- Строит порядок визитов, плановое прибытие, начало и окончание работ, заезды в сервисный центр
  (СЦ) за оборудованием.
- Разводит обеды двух смен, чтобы во время обеда одной работала другая.
- Объясняет каждое назначение: «почему этот сотрудник».

**Работа в течение дня**
- Перепланирует по событиям: новый наряд, отмена, задержка на объекте, передача в профильное
  подразделение, недоступность сотрудника, ход времени. Ответ на событие — десятые доли секунды.
- Не трогает выполненную и начатую часть плана.
- Заранее показывает риск опоздания и создаёт предупреждения за ≥ 30 минут до слота.
- Выявляет подозрения на групповую проблему (ПГП): ≥ 3 неисправностей с одного узла доступа за
  60 минут — и передаёт их в станционное подразделение вместо выезда.
- По нераспределённым нарядам объясняет причину и предлагает перенос со слотом.

**Интерфейс**
- Экран диспетчера: карта, диаграмма загрузки (Гант), списки нарядов, рисков, нераспределённых,
  смены и обеды, сценарии «что, если».
- Мобильная версия для сотрудника: маршрут на день, навигатор, отметки «позвонил / прибыл /
  завершил».
- Демо-день на синтетических данных — для показа без внешних данных.

## Быстрый старт

### Вариант А. Готовый комплект (без сборки, Windows)

Комплект `ado-transfer.zip` содержит готовые образы Docker, `compose.yaml` и копию базы.
Нужен Docker Desktop (Memory ≥ 4 ГБ в Settings → Resources, если будете поднимать GraphHopper).

```powershell
Expand-Archive .\ado-transfer.zip -DestinationPath .\ado-transfer
cd .\ado-transfer
docker load -i ado-images.tar                 # ado-app:latest и postgres:16-alpine
docker compose up -d --wait db

# только при первом запуске на этом компьютере, в пустую базу:
docker compose exec -T db pg_restore --exit-on-error --no-owner -U ado -d ado /backup/ado-db.dump

docker compose up -d app
```

Откройте **http://localhost:8080/ui/** и нажмите «демо-день».

> Проверить, есть ли уже данные в базе: `docker compose exec -T db psql -U ado -d ado -c "select count(*) from plan_versions"`.
> Если число больше нуля — `pg_restore` не нужен (повторно в заполненную базу его выполнять нельзя).

Дороги на карте — [GraphHopper](#карта-и-дороги-graphhopper--osrm):
```powershell
docker compose --profile graphhopper up -d --build graphhopper
docker compose logs -f graphhopper           # ждать строку «Server … Started»
```

Остановить, не удаляя базу: `docker compose --profile graphhopper stop`.
Следующий запуск: `docker compose up -d` (и при необходимости GraphHopper той же командой, что выше).

### Вариант Б. Из исходников через Docker Compose

```bash
cp .env.example .env
docker compose up --build             # app + PostgreSQL 16, миграции при старте контейнера
curl http://localhost:8080/api/v1/health
```

Нужен доступ к Docker Hub, npm и PyPI во время сборки. Интерфейс — http://localhost:8080/ui/,
Swagger по спецификации — http://localhost:8080/docs.

Опционально:
```bash
docker compose --profile graphhopper up -d   # дороги на карте (OSM УрФО ~380 МБ, граф строится несколько минут)
```

### Вариант В. Без Docker (разработка)

Python 3.12+, Node.js 20+.
```bash
python -m venv .venv && . .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -e ".[dev]"
cd frontend && npm install && npm run build && cd ..
uvicorn ado.api.app:app --port 8080
```
Без `ADO_DATABASE_URL` сервис работает только в памяти — для разработки этого достаточно.

## Интерфейс диспетчера

Адрес: **http://localhost:8080/ui/**. Экран обновляется сам (опрос раз в 2 с); при новой версии
плана строка показателей коротко подсвечивается.

### Стартовый экран и демо-день

Пока день не загружен, экран предлагает загрузить данные через API или нажать **«демо-день»**.

| Кнопка | Что делает |
|---|---|
| **демо-день** | Генерирует синтетический день (400 нарядов, 40 сотрудников, 5 СЦ) и строит план (~30 с) |
| **событие ▶** / **+10** | Проигрывает следующее событие сценария (или десять) — план перестраивается |
| **↻ перезапустить демо** | Начинает демо-день заново |
| **✕ выйти из демо** | Возвращает к дню, загруженному через API, или к стартовому экрану |
| **📱 сотрудник** | Открывает мобильную версию для выбранного сотрудника в новой вкладке |

Демо работает в **отдельном экземпляре сервиса в памяти**: день, загруженный через API, и история
в PostgreSQL не затрагиваются. В интерфейсе нет операций удаления данных.

### Строка показателей

`дата · ⏱ модельное время · план vN (событие) · успешно X/Y · доля % · в пути · CV загрузки ·
не распр. · риски · 🚦 пробки учтены (если включено) · нарушений`

- **Успешно** — визит начат в слот и закончен до контрольного срока, без нарушений; повторные
  обращения идут с весом 2.
- **CV загрузки** — коэффициент вариации загрузки сотрудников: чем меньше, тем равномернее.
- **Нарушений** — проверка каждой версии плана независимым валидатором (ограничения H1–H10);
  при ненуле подсказка показывает, какие нарушены.

### Карта

- **Точки нарядов** — цвет по статусу: синий — запланирован, оранжевый — выполняется, зелёный —
  выполнен, красный — не распределён. Красная обводка — риск опоздания. Жёлтые круги — СЦ.
- **Маршрут** выбранного сотрудника (клик по нему на карте или на диаграмме Ганта) или всех сразу
  (флажок «все маршруты»).
  - Если подключён сервер маршрутов — линия **по дорогам**; в подсказке длина и время в пути по
    данным движка.
  - Если не подключён — тонкий **пунктир «порядок объезда»** и плашка «Маршруты по дорогам
    недоступны» с причиной. Пунктир — это не дорога, и интерфейс так и пишет.
- **Карточка наряда** — клик по точке или по строке таблицы. Открывается поверх карты, не выходит
  за экран, длинный текст прокручивается; закрыть — × или Esc. В карточке:
  - адрес и координаты (из входных данных как есть), узел доступа;
  - слот, последний допустимый старт, контрольный срок, нужное оборудование;
  - статус, исполнитель, плановое прибытие и работы;
  - **«Почему этот сотрудник»** — прирост пути, сколько было других допустимых исполнителей, запас
    времени;
  - длительность по истории (если загружена), отметки сотрудника, причина нераспределения, риск.

### Вкладки справа

| Вкладка | Содержимое |
|---|---|
| **Наряды** | Все наряды дня с фильтрами: сотрудник, профиль, статус (в т. ч. «с риском опоздания»), интервал слота, поиск по номеру или адресу. Метки: «П» — повторное обращение, «2 чел.» — по регламенту выполняют двое, «📍 на месте» / «✅ отм.» — отметки сотрудника |
| **Риски** | Прогноз опоздания по текущему плану: «нарушение» (опоздание неизбежно) и «риск» (запас < 15 мин); предупреждения LATE_RISK с предложенным действием (передать другому / перенести со слотом); список «пора звонить абоненту» (за 60–30 мин до слота) |
| **Нераспределённые** | Наряды, которые не помещаются в смену: сводка по причинам, причина по каждому, предлагаемое действие и слот переноса |
| **Смены и обеды** | Смены, окна начала обеда из входных данных и окна, по которым строится план; «Непрерывная работа обеспечена» или причины, почему это невозможно |
| **Сценарии** | «Что, если»: не вышли N сотрудников; какой запас оборудования нужен, чтобы не заезжать в СЦ; с учётом пробок. Загрузка истории нарядов для прогноза длительности |
| **Маршрут** | Остановки выбранного сотрудника: тип, место, прибытие, начало, конец, статус, объяснение назначения |

### Диаграмма Ганта (внизу)

Строка — сотрудник, ось — время 8:00–21:30.
- Полосы визитов окрашены по статусу; серые — обед; бирюзовые — заезд в СЦ.
- Тонкие линии — дорога, пунктир — ожидание.
- Светлый фон — смена, жёлтый фон — когда может идти обед.
- Красный фон — сотрудник недоступен.
- Вертикальная красная линия — «сейчас».

Клик по подписи — выбрать сотрудника, по полосе — открыть наряд.

### Сообщения

- «Сервер рассчитывает план — данные обновятся по готовности»: идёт построение плана (до 300 с),
  экран не зависает.
- «Ошибка связи с сервером»: на экране остаётся последняя полученная версия плана с пометкой, что
  она может быть устаревшей.
- «Последнее событие …»: что произошло и как перестроен план.

## Мобильная версия для сотрудника

Адрес: **http://localhost:8080/ui/#tech/ST-001** (или кнопка «📱 сотрудник», или
`/ui/#tech` и выбор себя в списке). С телефона в той же сети:
`http://<IP компьютера>:8080/ui/#tech/ST-001`; на Windows может понадобиться разрешить входящие
подключения на порт 8080 в брандмауэре.

**Рабочий цикл по адресу**
1. Карточка «Следующий адрес»: адрес, вид работ, слот клиента, плановое время, оборудование.
2. **🧭 Навигатор** — маршрут к адресу в Яндекс Картах.
3. **📞 Позвонил абоненту** → **📍 Прибыл** (заголовок «Вы на адресе») → **✅ Завершил**
   (доступно только после «Прибыл»).
4. После «Завершил» экран сразу показывает следующий адрес («Заказ завершён. Следующий адрес: …,
   по плану в 10:00»), навигатор ведёт туда, полоса «Выполнено N из M» растёт.
5. После последнего — «На сегодня адресов больше нет» и «🧭 Навигатор в СЦ».
6. Ошиблись — повторное нажатие снимает отметку; у сделанного адреса в списке есть «↩».

Отметки видны диспетчеру в таблице и карточке наряда (со временем нажатия). План они **не
меняют**: в API кейса нет события «визит завершён», статусы визитов идут по модельному времени.

**Только в демо-дне** (в реальном дне события присылает оркестратор):
- **⏱ Задерживаюсь на 30 мин** — по начатому визиту отправляет событие `VISIT_DELAYED`;
- **🚗 Сломалась машина** — отправляет `STAFF_UNAVAILABLE`, наряды сотрудника перераспределяются
  (или уходят в нераспределённые, если ни у кого нет времени).

Авторизации нет — это демонстрационная версия.

## Загрузка своих данных

### Файлы организаторов

Положите файлы в один каталог, например `data/raw/` (он в `.gitignore`):

| Файл | Куда идёт |
|---|---|
| `service_centers.json`, `staff.json`, `access_nodes.json`, `work_types.csv` | `PUT /api/v1/reference` (одним объектом; CSV — массивом строк) |
| `travel_matrix.json` | `PUT /api/v1/reference/travel-matrix` |
| `orders_train.json` | `PUT /api/v1/days/{date}` — наряды дня со слотом в эту дату, зарегистрированные не позднее `now` |
| `events_example.json` | события сценария (поздние наряды приходят как `NEW_ORDER`) |

Загрузчик `ado.data.prepare.prepare_data` сам читает такой каталог и делит наряды по дням.

### Прогнать весь день одной командой (без сервера)

```bash
PYTHONPATH=src python benchmarks/files_day.py data/raw 60
```
Сравнивает три варианта алгоритма на одном дне, проигрывает все события, результат пишет в
`benchmarks/results/files_day.json`. Пример данных в формате организаторов (синтетика) —
`tests/fixtures/files_day/`.

### Против запущенного сервера (как это делает оркестратор)

```bash
PYTHONPATH=src python - <<'EOF'
import datetime
from ado.data.prepare import prepare_data, _read_json
from ado.orchestrator import http_client, run_day
ds = prepare_data("data/raw")
sc = _read_json("data/raw/events_example.json")
day_input, _ = ds.days[sc["date"]].day_input(datetime.time(8, 30))
res = run_day(http_client("http://localhost:8080"), ds.reference_raw,
              ds.travel_matrix_raw, day_input, sc, time_limit_sec=60)
print("ошибок:", res.errors)
EOF
```
После этого план, его версии и риски видны в интерфейсе.

> Повторная загрузка той же даты (`PUT /days/{date}`) по спецификации сбрасывает план и события
> этого дня, а в PostgreSQL заменяет историю даты. Для экспериментов используйте демо-день или
> отдельный стенд.

## Как устроено планирование

Подробная постановка — [docs/ADO_FORMALIZATION.md](docs/ADO_FORMALIZATION.md).

**Модель.** Динамическая задача маршрутизации с временными окнами (DVRPTW): разные допуски
сотрудников, обязательный обед, рюкзак оборудования с пополнением в любом открытом СЦ, заморозка
выполненной части. Время — целые секунды от полуночи дня (часовой пояс +05:00); время в пути — из
**единой матрицы** организаторов, как у их валидатора.

**Жёсткие ограничения H1–H10** (допуск, смена, перерыв, слот, норматив, дорога, оборудование,
СЦ, учёт каждого наряда ровно в одном месте, заморозка) проверяет один конструктор расписания —
`RouteSimulator`. Каждую версию плана независимо перепроверяет валидатор.

**Цель (лексикографически):** больше успешных нарядов (повторные с весом 2) → меньше переносов →
меньше времени в пути → равномернее загрузка.

**Алгоритм**

| Этап | Метод | Время |
|---|---|---|
| Начальный план | regret-3 вставка (сначала наряды с наименьшим выбором мест) | секунды |
| Улучшение | локальный поиск + ALNS (4 оператора разрушения × 2 восстановления, адаптивные веса, отжиг) | до `time_limit_sec` (≤ 300 с) |
| Событие | заморозка начатого → ремонт затронутых маршрутов → вставка освободившихся → локальное улучшение → «якоря» | ≤ 0.12 с на 400 нарядах (лимит 10 с) |

**Сравнение вариантов** (3 синтетических дня × 400 нарядов, `benchmarks/compare.py`):

| | Baseline (жадный) | Basic (regret + LS) | Full (+ ALNS) |
|---|---|---|---|
| Доля успешных (взвеш.) в конце дня | 0.431 | 0.528 | 0.570 |
| В пути, ч | 102 | 67 | 58 |
| Нарушений по вине алгоритма | 0 | 0 | 0 |

**ПГП.** Неисправности и деградации (`pgp_relevant`) с одного узла доступа: ≥ 3 за скользящее окно
60 минут. Группа не планируется к выезду, наряды передаются в станционное подразделение,
создаётся алерт `PGP_DETECTED`; начатые визиты остаются в маршруте. В интерфейсе ПГП скрыты по
решению команды, в API они есть. Показать: `docker compose exec app python scripts/demo_pgp.py`.

**Раннее предупреждение.** Прогноз начала каждого предстоящего визита по текущей
последовательности (с фактическими окончаниями из событий и, если загружена, с длительностями по
истории). Если наряд приходится передать другому сотруднику или снять, создаётся `LATE_RISK` —
своевременным считается предупреждение не позднее чем за 30 минут до слота.

**Нераспределённые наряды** остаются в плане (`unassigned`) с причиной и предложением, обычно
«перенос» на тот же слот в ближайший рабочий день. При каждом событии система снова пробует их
вставить. В следующий день сами не переносятся: состав дня присылает внешняя система, а перенос
согласует диспетчер.

**Обеды смен.** Окна начала обеда из `staff.json` сужаются (только внутри входного окна), чтобы
обеды смен не пересекались и во время обеда одной смены работала другая. Для смен кейса:
09–18 → начало обеда 12:00–14:00, 12–21 → 15:00–17:00. Если обеспечить это нельзя, ограничения не
нарушаются, а причина показывается во вкладке «Смены и обеды».

Все принятые решения и допущения — [docs/ADO_DECISIONS.md](docs/ADO_DECISIONS.md) (D1–D42).

## Карта и дороги: GraphHopper / OSRM

Подложка карты — тайлы OpenStreetMap, их загружает браузер пользователя (нужен интернет). Линии
маршрутов по дорогам строит отдельный сервис маршрутов.

**Свой GraphHopper (рекомендуется)** — [github.com/graphhopper/graphhopper](https://github.com/graphhopper/graphhopper):
```bash
docker compose --profile graphhopper up -d --build graphhopper
docker compose logs -f graphhopper
```
- Первый запуск собирает образ (GraphHopper 11.0, Java 21), скачивает OSM Уральского ФО с Geofabrik
  (~380 МБ) в папку `osm` и строит граф — несколько минут. Нужно 3–4 ГБ памяти.
- Скрипт проверяет, что скачана настоящая карта, а не страница ошибки.
- Карту можно скачать вручную
  (https://download.geofabrik.de/russia/ural-fed-district-latest.osm.pbf) и положить в `osm/` под
  именем `ural-fed-district-latest.osm.pbf`.
- Граф хранится в томе `gh-cache`, следующие запуски быстрые.

**Облачный GraphHopper** — `ADO_GRAPHHOPPER_URL=https://graphhopper.com/api/1` и
`ADO_GRAPHHOPPER_KEY=…`. Координаты остановок уходят на graphhopper.com, действуют лимиты тарифа.

**OSRM** — `ADO_GRAPHHOPPER_URL=` (пусто), `ADO_OSRM_URL=http://osrm:5000`,
`docker compose --profile osrm up` (нужен `data/osm/ural-fed-district-latest.osm.pbf`).

Важно: линия по дорогам **только рисуется**. Время в пути в плане и в проверках — всегда из
матрицы организаторов. Если сервис маршрутов недоступен, интерфейс показывает причину и подсказку
и не выдаёт прямые отрезки за дороги.

## Хранение данных (PostgreSQL)

При заданном `ADO_DATABASE_URL` сервис пишет в PostgreSQL 16 (миграции Alembic применяются при
старте контейнера):
- справочники и наряды дня;
- **каждую версию плана** с метриками, остановки маршрутов и нераспределённые;
- события (дубликаты отсекаются по `event_id`) и аудит изменений маршрутов.

Запись идёт в той же критической секции, что и публикация плана (оптимистическая блокировка). Ошибка
БД не ломает API: она логируется и видна в `/ui-api/state`.

Ограничение: активное состояние дня живёт в памяти приложения. После перезапуска контейнера история
остаётся в БД, но день на экран сам не возвращается — его нужно загрузить снова.

## Дополнительные задания кейса

| Задание | Статус | Где |
|---|---|---|
| Пробки по часам суток | ✅ | `ADO_TRAFFIC=1`; «Сценарии» → «с учётом пробок». Коэффициенты применяются по часу отправления, значения < 1 не используются (проверка H6 идёт по базовой матрице). По умолчанию выключено: базовая оценка кейса их не применяет |
| Прогноз длительности работ по истории | ✅ | Медиана фактических длительностей по сотруднику и типу работ (не меньше норматива). Используется в прогнозе рисков и карточке наряда; сам план — по нормативу (требование H5). История: `ADO_HISTORY_FILE` или загрузка во вкладке «Сценарии» |
| Совместные наряды (ВЛС, двое) | ❌ | В API кейса наряд может стоять только в одном маршруте — второго исполнителя не выразить. Наряды помечены «2 чел.», проект решения — D41 |
| Объяснимость назначения | ✅ | «Почему этот сотрудник» в карточке и во вкладке «Маршрут» |
| Мобильная версия для сотрудника | ✅ | `/ui/#tech/ST-001` |
| Сценарный анализ | ✅ | «Сценарии»: −N сотрудников, запас оборудования без заездов в СЦ, пробки |

## Разработка

### Структура репозитория

```
spec/                api_spec.yaml — источник истины по API
src/ado/
  domain/            модели, перечисления, время (секунды от полуночи), контракты
  data/              чтение и проверка входных данных, календарь, подготовка дня
  routing/           матрица (+ пробки), OSRM-таблицы, линии по дорогам (GraphHopper/OSRM)
  optimization/      ПГП, допуски, приоритеты, симулятор маршрута, вставка, начальный план,
                     LS + ALNS, оценка, валидатор, риски, обеды смен, длительности по истории
  events/            сессия дня: события, заморозка, перепланирование, предупреждения
  persistence/       PostgreSQL: DDL, хранилище версий, клиенты (SQLAlchemy / pgwire)
  api/               сервис по спецификации, ASGI-приложение, служебный API интерфейса
  scenarios.py       сценарный анализ
  synthetic.py       генератор синтетических данных в формате организаторов
  orchestrator.py    эмулятор оркестратора (сценарий дня по HTTP или в процессе)
frontend/            React + TypeScript + Leaflet, сборка esbuild → frontend/dist
tests/               unit · integration (PostgreSQL, полный день) · contract (схемы spec)
benchmarks/          сравнение вариантов, прогон дня по файлам, результаты
scripts/             rehearsal.py — репетиция развёртывания; demo_pgp.py — показ ПГП
migrations/          Alembic
docker/              entrypoint, Dockerfile.update (обновление образа офлайн), graphhopper/
docs/                постановка, спецификация, архитектура, контракты, решения, задачи, ревью, защита
```

### Команды

```bash
python -m pytest                               # тесты: 315 пройдено, 1 пропущен (нужен ADO_OSRM_URL)
ruff check . && ruff format --check .          # линтер и формат
cd frontend && npm run typecheck && npm run build

PYTHONPATH=src python benchmarks/compare.py 400 60 7 11 23     # Baseline / Basic / Full на 3 днях
PYTHONPATH=src python benchmarks/scenario_day.py 7 400 60      # полный день: события, время ответа
PYTHONPATH=src python benchmarks/files_day.py tests/fixtures/files_day 60
python scripts/rehearsal.py                                    # PostgreSQL + uvicorn + день по HTTP
```

Интеграционные тесты с PostgreSQL поднимают временный локальный сервер сами, если найден PostgreSQL 16
(`/usr/lib/postgresql/16/bin` или `ADO_PGBIN`, запуск от root на Linux); иначе они пропускаются.

### Обновление образа без доступа к реестрам

```bash
cd frontend && npm run build && cd ..
docker build -f docker/Dockerfile.update --build-arg BASE=ado-app:latest -t ado-app:latest .
```
Новый код и интерфейс кладутся поверх готового образа; зависимости Python берутся из него.

## Ограничения

- Данные организаторов не получены — качество измерено на синтетике.
- Совместные наряды не реализованы (ограничение API).
- Активный день после перезапуска контейнера не восстанавливается из БД.
- Мобильная версия — без авторизации; отметки хранятся в памяти и на план не влияют.
- Сборка образа с нуля (`docker compose up --build`) и запуск GraphHopper в среде разработки
  команды-автора не проверялись (не было доступа к реестрам); готовый комплект проверен.
- Адреса не геокодируются: используются координаты из входных данных.

## Решение проблем

| Симптом | Что сделать |
|---|---|
| `http://localhost:8080` не открывается | `docker compose ps`, `docker compose logs app`; порт 8080 занят — `docker ps`, остановить лишний контейнер |
| Карта: «GraphHopper недоступен … Name or service not known» | Сервер маршрутов не запущен: `docker compose --profile graphhopper up -d graphhopper` |
| GraphHopper долго не стартует | Идёт построение графа (минуты); смотреть `docker compose logs -f graphhopper`; `OutOfMemoryError` — дать Docker больше памяти |
| GraphHopper скачал «не карту» | Скачать файл в браузере и положить в `osm/ural-fed-district-latest.osm.pbf` |
| Карта серая, без улиц | Браузер не может загрузить тайлы OpenStreetMap — нет интернета |
| `pg_restore: … does not appear to be a valid archive` | Рядом с `compose.yaml` нет файла `ado-db.dump` (Docker создал вместо него папку): удалить папку, распаковать файл, `docker compose up -d --force-recreate db` |
| `pg_restore` ругается на существующие объекты | База уже восстановлена — повторять не нужно |
| После «Сломалась машина» заказы не ушли другим | При 400 нарядах маршруты у всех заполнены — заказы уходят в «Нераспределённые» с предложением переноса |
| Мобильная версия: «План на день ещё не построен» | Сначала «демо-день» или загрузка дня через API |
| С телефона не открывается | Телефон в той же сети; разрешить порт 8080 в брандмауэре Windows |
