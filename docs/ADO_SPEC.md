# ADO_SPEC — предметная область, ограничения, цели

Источник: ТЗ кейса «Умная диспетчеризация выездных бригад» (УрТИСИ СибГУТИ, ПАО «Ростелеком»,
2026) и `spec/api_spec.yaml` v1.0.0. При расхождении приоритет у спецификации API.

## 1. Сущности
- **Сервисный центр (СЦ)** — 5 шт., координаты, режим работы `open–close`, время пополнения АО
  `restock_duration_min`. Маршрут сотрудника начинается и заканчивается в его СЦ; пополнять АО
  можно в **любом** СЦ, открытом на всём интервале пополнения.
- **Сотрудник** — 40 шт. (28 × 3ЛТП, 12 × инсталляция). Профили `INSTALL`/`LTP3`, технологии
  `PON/FTTB/XDSL/DOCSIS`, допуск к высоте, смена (09–18 или 12–21) с перерывом 60 мин и окном
  начала перерыва, `equipment_start`, `equipment_capacity`.
- **Узел доступа** — OLT/SWITCH/DSLAM/CMTS со списком обслуживаемых домов. Используется для ПГП.
- **Дом** — `building_id`, тип `MKD/PRIVATE`, признак ВЛС (`overhead_line`).
- **Тип работ** — 8 кодов, норматив `duration_min`, `max_start_delay_min` (10 для инсталляций),
  вид срока и признак `pgp_relevant` (`REPAIR`, `DEGRADATION`).
- **Наряд** — тип, технология, дом, узел доступа, `registered_at`, слот 2 ч, `latest_start`,
  `deadline` (уже рассчитан организатором), требуемое АО, `is_repeat`.
- **Матрица времени в пути** — единая для всех команд, N×N по всем СЦ и домам, секунды и метры,
  может быть несимметричной; из точки в себя — 0.

| Код | Тип работ | Профиль | Норматив, мин |
|---|---|---|---|
| INST_PON_MKD | Инсталляция МКД PON | INSTALL | 90 |
| INST_FTTB_MKD | Инсталляция МКД FTTB | INSTALL | 60 |
| INST_PRIVATE_VLS | Инсталляция, частный сектор, ВЛС | INSTALL + высота | 180 |
| ADD_SERVICE | Доподключение услуги | INSTALL | 40 |
| SURVEY_PRIVATE | Обследование частного сектора | INSTALL / LTP3 | 45 |
| REPAIR | Устранение неисправности | LTP3 | 60 |
| DEGRADATION | Устранение деградации по мониторингу | LTP3 | 45 |
| DISMANTLE | Демонтаж АО | LTP3 | 30 |

Фактические значения берутся из `work_types.csv` (справочник важнее таблицы).

## 2. Жёсткие ограничения (H1–H10, п. 4 спецификации)
| Код | Суть |
|---|---|
| H1 | профиль ∈ `work_type.profiles`; технология ∈ `staff.technologies`; `requires_height` ⇒ `height_permit` |
| H2 | `DEPOT_START.start ≥ shift.start`, `DEPOT_END.arrival ≤ shift.end`, все остановки внутри смены |
| H3 | при наличии визитов — ровно один `BREAK` ≥ `break_duration_min`, начало в `break_window`, без пересечений |
| H4 | `slot.start ≤ VISIT.start ≤ latest_start` |
| H5 | `VISIT.end − VISIT.start = duration_min` (или время из `VISIT_DELAYED`/`ORDER_TRANSFERRED`) |
| H6 | `arrival(k) ≥ end(k−1) + travel(k−1→k)`, `start ≥ arrival`, `end ≥ start` |
| H7 | АО списывается в момент `start` визита, остаток ≥ 0, `RESTOCK` доводит до `equipment_capacity` |
| H8 | `DEPOT_*` — СЦ сотрудника; `RESTOCK` — любой СЦ, открытый на `[start, end]`, длительность ≥ `restock_duration_min` |
| H9 | каждый наряд дня ровно в одном месте: маршрут / `unassigned` / `pgp_groups` / `cancelled` |
| H10 | заморозка начатого между версиями плана (раздел 3 ниже) |

Структура: первая остановка `DEPOT_START`, последняя `DEPOT_END` (у недоступного — не обязательно);
`VISIT.location_id = building_id`; `BREAK.location_id` = точка предыдущей остановки, дорога 0;
`seq` = 1, 2, 3… без пропусков.

## 3. Модельное время и заморозка
- Текущее время — `now` из загрузки дня, затем `timestamp` последнего события. Системные часы не используются.
- Остановка с `start < t` начата: нельзя менять сотрудника, наряд, `location_id`, `arrival`, `start`;
  `end` — только по `VISIT_DELAYED` / `ORDER_TRANSFERRED`.
- Новая или переставленная остановка: `arrival ≥ max(end предшественника, t) + travel`.
- Визит по `NEW_ORDER` начинается не раньше `timestamp` события.
- Отменённый (`ORDER_CANCELLED`) неначатый наряд не посещается.
- `STAFF_UNAVAILABLE`: нет остановок, начинающихся в период недоступности; после `until` сотрудник
  продолжает смену **из своего СЦ**.

## 4. Цели (по убыванию приоритета)
1. Визиты в согласованный слот и наряды в контрольный срок; повторные обращения — вес 2.
2. Минимум переносов.
3. Минимум суммарного времени в пути.
4. Равномерная загрузка (коэффициент вариации `utilization = (работы + дорога) / (смена − перерыв)`).

Наряд успешен, если визит начат в `[slot.start, latest_start]`, завершён не позднее `deadline` и не
нарушает H1–H10. Генератор гарантирует `latest_start + duration ≤ deadline`, поэтому на практике
успех = визит по нормативу в окне начала (см. D7).

## 5. Оценка (ТЗ п. 6 + спецификация п. 5)
| Критерий | Вес |
|---|---|
| Доля успешных нарядов (вес повторных 2) | 35% |
| Суммарное время в пути | 15% |
| Равномерность загрузки (CV) | 5% |
| Реакция на события: сроки после событий, время ответа, своевременность предупреждений, ПГП | 15% |
| Интерфейс диспетчера (экспертно) | 15% |
| Архитектура, код, документация, презентация (экспертно) | 15% |

- План > 300 с — день не оценивается автоматически; событие > 10 с — не обработано в срок.
- `LATE_RISK` своевременен, если `created_at ≤ slot.start − 30 мин`; оценивается по нарядам, которые
  после событий переназначены другому сотруднику или сняты из маршрута.
- ПГП сравниваются с эталоном по составу (точность/полнота) и моменту `detected_at`.
- Скрытый набор: 3 дня × 350–450 нарядов + поток событий с ПГП.

## 6. ПГП
Эталон: не менее 3 нарядов `pgp_relevant` с одного узла доступа, зарегистрированных в пределах
60 минут; случайных совпадений — не более 2 за 60 минут. Группа не распределяется по сотрудникам,
`action = TRANSFER_TO_STATION`. Наряд ПГП с уже начатым визитом остаётся в маршруте и в группу не входит.
`detected_at` не меняется при пополнении группы.

## 7. События
`NEW_ORDER`, `ORDER_CANCELLED`, `VISIT_DELAYED`, `ORDER_TRANSFERRED`, `STAFF_UNAVAILABLE`, `TIME_TICK`.
Порядок — неубывание `timestamp`; повтор `event_id` идемпотентен (`duplicate = true`, тот же
`plan_version`); каждое принятое событие — `plan_version + 1`. Противоречащее состоянию — `422`.
`VISIT_DELAYED`/`ORDER_TRANSFERRED` оркестратор генерирует из триггеров **по нашему плану**
(`timestamp = VISIT.start + fire_after_start_min`).

## 8. Процессные правила из ТЗ (в оценке API явно не проверяются)
- Звонок абоненту за 30–60 мин до слота; перенос — не позднее чем за 30 мин до слота.
- 3ЛТП проверяет все услуги; повреждение вне зоны ответственности — передача в профильное подразделение
  (в API — событие `ORDER_TRANSFERRED`).
