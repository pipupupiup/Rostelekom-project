# ADO_DECISIONS — решения, допущения, открытые вопросы

Обозначения: **D** — принятое решение, **A** — допущение (наша трактовка, не требование
организаторов), **Q** — вопрос к организаторам.

## Решения

**D1. `spec/api_spec.yaml` — источник истины.** Внутренний документ ADO (декомпозиция
алгоритма) скорректирован там, где он расходится со спецификацией (D2, D5, D10, D11).

**D2. Время в пути — единая матрица организаторов, а не OSRM.** Матрица приходит через
`PUT /reference/travel-matrix`, ею же валидатор проверяет H6. Любой другой источник даст
расхождения и нарушения H6. OSRM (ADO-02 в исходном плане) остаётся опциональным: геометрия
линий для карты в UI и генерация матрицы для собственных синтетических тестов. Новые адреса из
`NEW_ORDER` — дома из реестра `access_nodes[].buildings[]`, они уже есть в матрице; отсутствие
точки — ошибка данных (`422`), а не повод идти в сеть.

**D3. Внутреннее время — `int` секунд от местной полуночи дня плана.** Мастер-промпт допускает
минуты, но матрица задана в секундах, а допуск валидатора — 1 с; округление до минут копит
ошибку H6. На границах API — timezone-aware `datetime`, вывод в `+05:00`.

**D4. Два слоя моделей.** Домен (`ado.domain`) — неизменяемые dataclass'ы со `slots` для
горячего пути. Схемы API — pydantic в `ado.api.schemas` (ADO-16), с точными именами полей
спецификации. Преобразование — только в ADO-01 (вход) и ADO-16 (выход).

**D5. Актуальное состояние дня — в памяти процесса; PostgreSQL — журнал версий вне горячего
пути.** Лимит на событие 10 с, а `GET /plan` должен сразу отражать последнее событие. Запись
версии в БД — после формирования ответа (или в фоне); при недоступности БД сервис продолжает
работать (оценка от БД не зависит). Оптимистическая блокировка — по `plan_version`. Сервис
однопроцессный (`--workers 1`), т. к. состояние в памяти.

**D6. Один конструктор расписаний + независимый оракул.** Расписание маршрута строит только
`simulate_route()` (ADO-07); все оптимизаторы получают допустимость только от него.
`validate_plan()` (ADO-11) — *независимая* проверка готового плана H1–H10 по образцу валидатора
организаторов, без симулятора (уточнено: задания ADO-09/17/20 требуют независимый валидатор).
Это единственное разрешённое дублирование правил: оракул ловит ошибки конструктора. Валидатор
вызывается перед публикацией версии, в тестах и бенчмарках, не во внутренних циклах.

**D7. Целевая функция — лексикографическая** (`PlanMetrics.key()`): нарушения → взвешенные
успехи → переносы → время в пути → CV загрузки. Поскольку генератор гарантирует
`latest_start + duration ≤ deadline` и все наряды дня имеют слот сегодня, успех наряда
эквивалентен визиту в окне `[slot.start, latest_start]` по нормативу. Отдельная оптимизация
контрольного срока не нужна, но проверка `end ≤ deadline` остаётся в симуляции.
Внутри эвристик допускается скалярная свёртка с весами, сохраняющими этот порядок.

**D8. Основной алгоритм — собственный: Regret Insertion → Local Search → ALNS**, как в
декомпозиции ADO. Причина: нестандартные ограничения (перерыв как остановка на месте
предыдущей, пополнение «до capacity» в любом открытом СЦ, заморозка префикса) проще и надёжнее
выражаются в собственной симуляции. OR-Tools — зависимость для подзадач и как эталон для
сравнения в ADO-17.

**D9. ПГП — детерминированное правило до оптимизации:** ≥ 3 наряда `pgp_relevant` с одного
`access_node_id`, `registered_at` в пределах 60 мин (скользящее окно). Разброс регистрации внутри
группы не превышает окно (эталон: «в пределах 60 минут»; без этого ограничения к группе
цеплялись случайные обращения — точность падала до 0,75 на синтетике). Новые наряды узла
присоединяются к группе, если разброс остаётся ≤ окна; `detected_at` не меняется. Наряд с
начатым визитом в группу не включается.

**D10. Контрольные сроки не пересчитываем.** `latest_start` и `deadline` приходят рассчитанными
(с производственным календарём). ADO-01 только проверяет согласованность
(`latest_start = min(slot.end, slot.start + max_start_delay)`) и логирует расхождения.

**D11. Коэффициенты пробок (`hourly_factors`) по умолчанию выключены.** Валидатор проверяет H6
по матрице без коэффициентов. Включаются флагом только как более осторожный прогноз в
`DelayPredictor` и в сценарном анализе.

**D12. Перерыв — явная остановка `BREAK`** на месте предыдущей остановки, ровно одна при наличии
визитов, начало в `break_window`. Перерыв вставляется в «естественный» промежуток ожидания, если
он есть.

**D13. `seq` не хранится в домене** — вычисляется при сериализации как позиция + 1.

**D14. Предупреждения `LATE_RISK`.** Создаются (а) как только прогноз начала визита превышает
`latest_start`, (б) **всегда** при переназначении или снятии наряда из маршрута после события —
именно по таким нарядам оценивается своевременность. Если сервис сам применил решение —
`applied = true`, `status = RESOLVED`. Алерты только добавляются.

**D15. ПГП: начатые визиты засчитываются в порог, но не входят в группу.** Они свидетельствуют
об инциденте; спецификация требует оставить их в маршруте. Группа создаётся, если в ней ≥ 2
нарядов (`order_ids.minItems = 2`). Наряд, зарегистрированный в пределах окна от участника
существующей группы, присоединяется к ней — результат не зависит от истории вызовов.

**D16. OSRM — опциональный адаптер.** `OsrmTableClient` + `OsrmMatrixCache` реализованы по
заданию ADO-02 (батчи, кеш, недостающие элементы, явные недостижимые пары), но в оцениваемом
прогоне не используются (D2). Подмены прямой линией нет нигде: недостижимая пара → `None` →
недопустимая поездка.

**D17. Размещение перерыва — жадное с откатом.** Симулятор ставит перерыв, когда он бесплатен
(в ожидании) или иначе не поместится; при нарушении перебирает альтернативные позиции. Возможен
редкий пропуск допустимого расписания (перерыв ещё раньше), но недопустимых маршрутов это не даёт.

**D18. Задание ADO-08 отсутствует** (`promt8.txt` = копия `promt7.txt`). Вставка реализована по
разделу 9 декомпозиции ADO: предпроверка (forward slack + остатки АО) → симуляция кандидатов по
возрастанию прироста дороги → RESTOCK в ближайшем открытом СЦ при нехватке.

**D19. Regret-k для ADO-09.** `score = вес · (Σ_{j=2..3}(c_j − c_1) + 600 с · priority)`,
отсутствующая альтернатива = `c_1 + 4 ч`. Ценность (вес) — множитель, а не скрытый штраф: при
равной структуре альтернатив повторное обращение назначается раньше. Стоимость `c` — прирост
времени в пути, с.

**D20. Минимальное вмешательство при событиях.** После события: (1) пересчёт и перестройка
порядка внутри затронутого маршрута; (2) вытесненные наряды — regret-вставка по всем допущенным;
(3) вставка нераспределённых и перестановки *внутри* изменённых маршрутов. Межмаршрутных
переносов «ради экономии дороги» нет: каждое переназначение должно сопровождаться своевременным
`LATE_RISK` (оценивается по переназначенным), а лишние переносы нарушают договорённости с
абонентами. ALNS работает только на первоначальном плане.

**D21. Устойчивое размещение обеда.** Перерыв не откладывается за остановку, после которой до
конца окна перерыва остаётся меньше `break_margin` (60 мин), если сейчас его можно взять без
нарушения слота следующего визита. Найдено на сценарном прогоне: задержка визита 13:00–14:30 до
15:30 при окне 12–15 сделала обед невозможным (H3). После правила таких нарушений по вине плана
нет; дорога и успех на первоначальном плане не изменились заметно.

**D22. API без автоматической валидации фреймворка.** Тела читаются как JSON, проверку выполняет
ADO-01 (путь к полю в `ErrorResponse.details`, разделение 400/422). FastAPI-валидация дала бы
собственный формат 422, не совпадающий со спецификацией. Соответствие ответов схемам проверяют
контрактные тесты (jsonschema по `api_spec.yaml`). Приложение собирается на FastAPI, если он
установлен (Docker), иначе на Starlette с теми же маршрутами (локальные тесты).

**D23. Одна блокировка на изменения.** Оркестратор шлёт запросы последовательно; одновременные
запросы (UI, повторы) сериализуются `RLock` в `DispatchService`. Тяжёлые вызовы идут в пуле
потоков, `/health` отвечает во время расчёта плана.

**D24. Интерфейс диспетчера.** React + TypeScript + Leaflet, сборка esbuild (без Vite — меньше
зависимостей), раздаётся тем же сервисом по `/ui/`. Данные — `GET /ui-api/state` (опрос раз в
2 с, `?since_version=` — без передачи плана, если версия не изменилась): справочники, наряды,
план в формате спецификации, риски ADO-12, метрики ADO-11. Фронтенд ничего не пересчитывает:
линии маршрутов — схема последовательности остановок, а не дорожная геометрия. Демо-режим
(`/ui-api/demo/*`) — только синтетические данные, с явной пометкой «СИНТЕТИКА» в интерфейсе.
Для локальной проверки без доступа к npm есть сборка `--offline` с заглушкой карты
(`frontend/dev/leaflet-offline.ts`), в рабочую сборку она не попадает.

**D25. «Повышенный риск» (HIGH) — только при отклонении от плана.** Узкое окно начала
инсталляции (10 мин) само по себе не риск: план его соблюдает. HIGH выставляется, если прогноз
начала позже планового и запас < 15 мин; VIOLATION — всегда при отрицательном запасе.

## Допущения

**A1. «Перенос» для метрики** = наряд в `unassigned` с `suggested_action = RESCHEDULE` плюс наряд,
снятый из маршрута после события. Валидатор организаторов может считать иначе.

**A2. Пустой маршрут.** Сотрудник на смене без визитов получает маршрут с пустым `stops`
(разрешено описанием `Route.stops`) — без `DEPOT_START`/`DEPOT_END`, чтобы не создавать лишних
проверок H2/H3.

**A3. Выезд не раньше `max(now, shift.start)`.** Первоначальный план строится на `now` (≈ 08:30)
до начала смен, поэтому ограничение не действует до первого события.

**A4. Прогнозируемая длительность (доп. задание) не подменяет норматив в плане** — H5 требует
`end − start = duration_min`. Прогноз используется только в `DelayPredictor` для раннего
предупреждения.

**A5. «N рабочих дней»** = сдвиг момента регистрации на N рабочих дней с сохранением времени
суток. Проверено на примере спецификации (22.10 14:12 + 3 → 27.10 14:12).

**A6. Праздники РФ 2026** заданы в `data/calendar.py` (1–11 янв., 23 фев., 9 мар., 1 и 11 мая,
12 июн., 4 ноя., 31 дек.). Используются только для сверки сроков (D10) и предложения слота
переноса. Расхождение со сроком во входе — предупреждение, вход побеждает.

**A7. Оценка ПГП-нарядов.** Наряды групп не считаются выполненными и исключаются из
знаменателя доли успеха (их оценивает отдельная ПГП-метрика). Так же — отменённые.

**A8. Предлагаемый слот переноса** — тот же интервал в ближайший рабочий день.

**A9. Выбывший по событию сотрудник** (`STAFF_UNAVAILABLE`) не обязан иметь обеденный перерыв
(вопрос Q3); при возвращении (`until`) выезжает из своего СЦ не раньше `until`.

**A10. Событие, продлившее начатый визит за конец смены или окна перерыва**, даёт неустранимое
нарушение H2/H3: начатую остановку менять нельзя (H10). Маршрут публикуется как есть (выполненная
часть + возвращение), остальные наряды перераспределяются.

**D26. Хранение плана (ADO-15).** PostgreSQL: `plan_versions` (JSON версии + метрики),
`plan_current` (указатель, `SELECT … FOR UPDATE` — оптимистическая блокировка, иначе
`VersionConflict`), `events` (PK `(date, event_id)` — дедупликация на уровне БД), `plan_stops`
(частичный уникальный индекс: один визит на наряд в версии), `route_audit`. DDL — один источник
(`persistence/ddl.py`), его выполняет и миграция Alembic, и тесты.

**D27. Запись в БД синхронно и не ломает API.** Версия пишется под той же блокировкой сразу после
расчёта (порядок версий в БД = порядок событий). Ошибка БД логируется (`db_errors`, статус в
`/ui-api/state`) и не меняет ответ API: оценивается API, а не хранилище. Время записи — этап
`persist` в `stages_ms`.

**D28. Два клиента PostgreSQL.** В Docker — SQLAlchemy + psycopg; для тестов без пакетов —
собственный клиент протокола pgwire (simple query, trust/cleartext/md5). Интерфейс общий (`Database`).

**D29. Варианты для сравнения (ADO-17).** Baseline — жадный ближайший без улучшений и с наивной
обработкой событий; Basic — regret-3 + LS, события с минимальным вмешательством; Full — + ALNS,
прогноз задержек и LATE_RISK. Одна и та же синтетика и один сценарий для всех.

**D30. `/ui-api/state` не ждёт расчёта.** Если блокировка занята дольше 0.5 с (идёт построение
плана), ответ `{"busy": true}`; интерфейс показывает «идёт расчёт» и не копит запросы.

**D31. Снятие наряда в ПГП — тоже LATE_RISK** (действие `TRANSFER_TO_STATION`, сразу
`RESOLVED`), чтобы диспетчер видел, что выезд по наряду отменён и он ушёл в станционное.

**D32. Оператор «якоря».** По спецификации `BREAK` стоит на месте предыдущей остановки с дорогой 0,
поэтому сотрудник без утренних визитов обедает в СЦ и не успевает к визиту с узким окном сразу
после обеда (ВЛС 13:00–13:10 на файлах `tests/fixtures/files_day`). Оператор переносит к нему
соседний наряд (≤ 15 мин езды) и вставляет нераспределённый следом; принимается, только если оба
маршрута допустимы (+1 выполненный). В построении плана — в LS; при событии — только якоря из
изменённых маршрутов (ответ на событие ≤ 0.12 с на 400 нарядах).

**D33. ПГП не показываются в интерфейсе диспетчера.** По требованию заказчика интерфейса вкладка,
легенда, показатель и статус «ПГП» убраны; наряды из `pgp_groups`, `PGP_DETECTED` и LATE_RISK о
снятии в ПГП на экран не выводятся, части сообщений о ПГП вырезаются. Серверная часть не менялась:
`spec/api_spec.yaml` требует `pgp_groups` в плане (H9), `PGP_DETECTED` и оценку ПГП (15 %).

**D34. Демо-день — отдельный сервис в памяти.** Раньше демо загружалось в основной сервис: заменяло
день из API и через `save_day` удаляло историю этой даты в PostgreSQL. Теперь демо — отдельный
`DispatchService` без БД; `/ui-api/state` показывает его, пока оно активно. `POST /ui-api/demo/exit`
возвращает экран к дню из API или к стартовому экрану и ничего не удаляет.

**D35. Дорожная геометрия — только для отображения (движок — D37).** `GET /ui-api/route-geometry`
строит линию по остановкам маршрута (`/route/v1/driving/…?overview=full&geometries=geojson`) вне
блокировки сервиса, с кешем и паузой 30 с после ошибки связи. Настройка — `ADO_OSRM_URL`. Нет
настройки или OSRM недоступен — `available: false` с причиной; UI пишет её и рисует только пунктир
«порядок объезда», подписанный как не дорога. Время в пути плана — по-прежнему матрица (D2).
Привязка точки к дороге дальше 300 м показывается в подсказке.

**D36. Разведение обедов смен.** `optimization/breaks.py`: группы сотрудников по смене; окно начала
обеда сужается (только внутри входного окна, длительность не меняется) так, чтобы (1) обед группы
целиком приходился на время, когда на смене другая группа, и (2) обеды групп не пересекались
(деление пересечения точкой, максимизирующей меньшее окно). Суженные окна получает симулятор; план
проверяется и по ним, и по входным (тест `test_files_day_breaks_staggered_within_input_windows`).
Невозможное (одна смена, окна нельзя развести, нет другой смены во время обеда, нет профиля в
другой смене) — `BreakPlan.issues`, показывается в UI. Отключение — `ReoptConfig.stagger_breaks`.
Для смен кейса: 09–18 → начало обеда 12:00–14:00, 12–21 → 15:00–17:00 (исходно обеды могли
совпасть 15:00–16:00, а обед второй смены — прийтись на 18:00–19:00, когда первой уже нет).

**D37. Основной движок дорожной геометрии — GraphHopper** (по выбору команды). `routing/geometry.py`:
`GraphHopperRouteClient` (`GET /route?point=lat,lon…&profile=car&points_encoded=false
&instructions=false`, разбор `paths[0].points` как GeoJSON или массива `[lon, lat, ele]`, время из мс,
«привязка» — расстояние от точки до `snapped_waypoints`), `OsrmRouteClient` — запасной.
`routing_from_settings`: `ADO_GRAPHHOPPER_URL` → GraphHopper (+ `ADO_GRAPHHOPPER_KEY` для облака),
иначе `ADO_OSRM_URL` → OSRM, иначе «не настроено». Свой сервер — `docker/graphhopper` (jar 11.0 с
Maven Central, Java 21, профиль `car` с CH, OSM УрФО с Geofabrik, кеш графа в томе), compose-профиль
`graphhopper`; в compose `app` по умолчанию смотрит на `http://graphhopper:8989`, при недоступности
сообщение подсказывает команду запуска. Сборка образа GraphHopper и импорт OSM в песочнице не
проверены (нет доступа к Maven Central, Docker Hub и Geofabrik) — проверены клиент и UI на тестовом
транспорте в формате ответа GraphHopper.

**D38. Загруженность дорог по часам (доп. задание).** `hourly_factors` матрицы применяются к
поездке по часу **отправления** (`TrafficTravelProvider.factor_at`, симулятор и прогноз рисков).
Коэффициенты < 1 не применяются: H6 проверяется по базовой матрице, более короткая поездка дала бы
нарушение. Базовое время остаётся нижней оценкой для отсечений. По умолчанию выключено
(`ADO_TRAFFIC=1` — включить): базовая оценка кейса коэффициенты не применяет, а учёт делает план
осторожнее. Сравнение «с пробками / без» — сценарий `traffic` (D40).

**D39. Прогноз длительности работ по истории (доп. задание).** `optimization/durations.py`: медиана
фактических длительностей сотрудника по типу работ, сглаженная к медиане по типу
(`w = n/(n+5)`), не меньше норматива; мало истории — норматив. План строится по нормативу — этого
требует H5 спецификации; прогноз применяется в раннем предупреждении (`forecast_route(durations=…)`)
и в карточке наряда. История: `ADO_HISTORY_FILE` (orders_train.json с `fact`) при старте или
`POST /ui-api/history` (загрузка файла во вкладке «Сценарии»); в демо — синтетическая история
(`synthetic.generate_history`: скорость зависит от стажа, в среднем около норматива).

**D40. Сценарный анализ (доп. задание).** `scenarios.py`, `POST /ui-api/scenario`: начало дня
пересчитывается быстрым алгоритмом (regret + LS) для базы и для сценария: `fewer_staff` (n
случайных сотрудников не вышли, 3 прогона), `backpack` (сколько АО взять, чтобы не заезжать в СЦ:
наибольшая потребность по маршрутам, не больше вместимости; план с таким запасом), `traffic`.
Активный план и история не меняются.

**D41. Совместные наряды не реализованы.** ВЛС в частном секторе по регламенту — двое
одновременно, но в API кейса наряд может быть ровно в одном маршруте (H9), второй сотрудник не
выражается в плане, и валидатор его не учтёт. Интерфейс помечает такие наряды «2 чел.» и
объясняет ограничение. Проект решения при расширении API: остановка `VISIT` с `helper_staff_id`
во втором маршруте; в симуляторе — синхронизация `start` двух маршрутов (совместное окно = пересечение
доступности), вставка пары маршрутов одной операцией (regret по парам сотрудников с допуском к
высоте), при событиях — заморозка обоих.

**D42. Мобильная версия сотрудника.** `/ui/#tech/ST-001`: маршрут на день, следующий адрес,
навигация (Яндекс Карты по координатам), отметки «позвонил / прибыл / завершил»
(`POST /ui-api/tech/mark`, `undo` — снять). Рабочий цикл: 📞 → 🧭 → 📍 прибыл → ✅ завершил (только
после «прибыл») → экран сразу переходит к следующему адресу маршрута, навигатор ведёт туда; после
последнего — «адресов больше нет», навигатор в СЦ. Отметки видны диспетчеру (таблица «✅ отм.»,
«📍 на месте», карточка — время нажатия) и приходят даже без новой версии плана. План отметки не
меняют: в API кейса нет события «визит завершён», статусы визитов в плане идут по модельному
времени (в демо часы модели стоят, пока не нажато «событие ▶»). В демо-дне кнопки «задерживаюсь» и «сломалась машина» отправляют события API
`VISIT_DELAYED` / `STAFF_UNAVAILABLE` (`POST /ui-api/tech/event`) — план перестраивается; в
реальном дне события присылает оркестратор, кнопки отключены. Авторизации нет — это демо.
