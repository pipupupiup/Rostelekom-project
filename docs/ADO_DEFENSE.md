## Подготовка стенда (за 30 минут до защиты)

1. `docker load -i ado-images.tar`, `docker compose up -d` — сервис на `http://localhost:8080/ui/`.
2. Дороги: `docker compose --profile graphhopper up -d graphhopper`, дождаться в
   `docker compose logs -f graphhopper` строки `Server … Started` (несколько минут). Без него карта
   честно пишет «маршруты по дорогам недоступны» и рисует пунктир — это тоже можно показать.
3. Пробки для демонстрации Д1 в самом плане: `$env:ADO_TRAFFIC="1"; docker compose up -d app`
   (иначе — только через «Сценарии»).
4. Открыть заранее две вкладки: диспетчер (`/ui/`) и сотрудник (`/ui/#tech/ST-004`, узкое окно или
   телефон в той же сети — `http://<IP ноутбука>:8080/ui/#tech/ST-004`).
5. Нажать «демо-день» заранее (план строится ~30 с). Демо работает в памяти и не трогает базу.

## Сценарий показа (≈ 10 минут)

### О1. Формализация (1 мин, слайд)
Показать `docs/ADO_FORMALIZATION.md`: DVRPTW с ресурсами; H1–H10; лексикографическая цель
(успешные с весом 2 → переносы → дорога → равномерность); regret-3 + LS + ALNS и почему не MILP
(10 с на событие, нестандартные ограничения). Цифра для слайда: Full 0.570 / Basic 0.528 /
Baseline 0.431 доли успешных, в пути 58 / 67 / 102 ч, 0 нарушений (`benchmarks/results/compare_summary.md`).

### О2. План смены (2 мин)
1. «демо-день» → верхняя строка: успешно N/M, в пути, CV загрузки, **нарушений 0**.
2. Клик по сотруднику на Ганте → маршрут на карте и вкладка «Маршрут»: DEPOT_START → визиты с
   плановым прибытием/началом/окончанием → **BREAK** → **RESTOCK** (заезд в СЦ, зелёный на Ганте,
   если есть) → DEPOT_END.
3. Сказать: каждый маршрут проверен независимым валидатором H1–H10.

### Д4. Объяснимость (30 с)
Клик по наряду (точка на карте или строка таблицы) → карточка: «Почему этот сотрудник: прирост
пути +N мин; других допустимых исполнителей на момент назначения: K; запас до последнего начала
M мин». Во вкладке «Нераспределённые» — причина и предложение (перенос на завтра со слотом).

### О3. Перепланирование и раннее предупреждение (2 мин)
1. «событие ▶» несколько раз / «+10» → баннер «Последнее событие …», версия плана растёт,
   показатели мигают; выполненные визиты (зелёные) не меняются — заморозка H10.
2. Вкладка «Риски»: прогноз опоздания по текущему плану (VIOLATION / HIGH) и предупреждения
   LATE_RISK с действием (передать / перенос со слотом) — создаются за ≥ 30 мин до слота.
3. Сказать: ответ на событие ≤ 0.12 с при лимите 10 с.

### Д5. Мобильная версия сотрудника (1.5 мин)
1. Вкладка сотрудника `/ui/#tech/ST-004`: следующий адрес, «🧭 Навигатор» (Яндекс Карты),
   маршрут на день.
2. Рабочий цикл по адресу: «📞 Позвонил» → «📍 Прибыл» (заголовок «Вы на адресе») →
   «✅ Завершил» → экран сразу показывает следующий адрес («Заказ завершён. Следующий адрес: …,
   по плану в 10:00»), навигатор ведёт туда, полоса «Выполнено 1 из 7». После последнего —
   «адресов больше нет» и навигатор в СЦ. Ошиблись — «↩» в списке снимает отметку.
   У диспетчера в таблице нарядов появляются «📍 на месте» / «✅ отм.», в карточке — время нажатия.
   Сказать: план отметки не меняют — в API кейса нет события «визит завершён», статусы плана идут
   по модельному времени; в реальном потоке это время событий оркестратора.
3. «🚗 Сломалась машина» → событие API `STAFF_UNAVAILABLE` → у диспетчера новая версия плана, наряды
   сотрудника перераспределены, его строка на Ганте — недоступен. («⏱ Задерживаюсь» работает
   на начатом визите → `VISIT_DELAYED`.)

### Д6, Д1, Д2. Сценарии (2 мин) — вкладка «Сценарии»
1. «на смену не вышли 3 сотрудника → рассчитать»: −N выполненных, +N нераспределённых, три прогона
   с перечнем отсутствующих.
2. «какой запас АО нужен»: рекомендация ONT/роутер/приставка и «заездов в СЦ: было X — стало 0».
3. «с учётом пробок по часам»: меньше выполненных, больше часов в дороге (коэффициенты 8:00 × 1.35,
   17:00 × 1.3 из матрицы).
4. Ниже — модель истории: N выполненных нарядов, медиана по типам; в карточке наряда «норматив
   60 мин, по истории ≈ 69 мин»; во вкладке «Риски» — «длительность в прогнозе: по истории». Сказать:
   план — по нормативу (этого требует H5 API), история сдвигает прогноз и раньше показывает риск.
   Реальную историю загрузить кнопкой «загрузить orders_train.json» (поле `fact`).

### О4. ПГП (1 мин) — терминал
`docker compose exec app python scripts/demo_pgp.py` (или из исходников:
`PYTHONPATH=src python scripts/demo_pgp.py`) — сервис в памяти внутри скрипта, базу и загруженный
день не трогает: группа на старте дня (узел, 3 наряда, TRANSFER_TO_STATION, алерт PGP_DETECTED), новые
группы появляются на событиях NEW_ORDER, итог «инцидентов найдено 3/3, наряды ПГП в маршрутах: 0».
В интерфейсе ПГП скрыты по решению команды; в ответе API (`pgp_groups`, `alerts`) они есть.

### О5. API (30 с)
`http://localhost:8080/docs` — Swagger по спецификации организаторов (`spec/api_spec.yaml`): health,
reference, travel-matrix, days, plan, events; «Try it out» — запросы к этому же сервису (GET /health,
GET /days/{date}/plan безопасны; PUT сбрасывают загруженный день — по спецификации).
Сказать: каждый ответ в тестах проверяется по JSON-схемам `spec/api_spec.yaml`
(`tests/contract/`), коды ошибок 400/404/409/422 по спецификации.

### О7. Контейнеры и документация (30 с)
`docker compose up -d` — app + PostgreSQL 16 (история версий плана, событий, аудит маршрутов);
README, `docs/` (спецификация, архитектура, контракты, решения D1–D42, ревью, этот файл).

### Д3. Совместные наряды (30 с, честно)
В таблице нарядов метка «2 чел.» у ВЛС, в карточке — объяснение: API кейса допускает наряд только
в одном маршруте (H9), второго сотрудника негде указать, валидатор его не учтёт. Проект решения —
D41 (синхронный визит в двух маршрутах, вставка пар сотрудников).

## Что сказать об ограничениях
* Данные — синтетика; на данных организаторов прогон делается одной командой
  `PYTHONPATH=src python benchmarks/files_day.py data/raw 60`.
* Дороги на карте зависят от сервера GraphHopper (или облачного ключа); время в плане — всегда по
  матрице организаторов.
* Мобильная версия — без авторизации (демо); отметки хранятся в памяти сервиса.
* После перезапуска контейнера активный день из БД на экран не возвращается (история — в БД).
