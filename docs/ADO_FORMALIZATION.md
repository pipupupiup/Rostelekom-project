# ADO_FORMALIZATION — постановка задачи, ограничения, целевая функция, выбор метода

Задача кейса — динамическая задача маршрутизации неоднородного парка с временными окнами
(**DVRPTW**) с дополнительными ресурсами: допуски сотрудников, обеденный перерыв, оборудование в
«рюкзаке» с пополнением в сервисных центрах (multi-trip), заморозка выполненной части при
перепланировании и выявление групповых аварий (ПГП). Ниже — формальная модель, по которой написан
код (`src/ado/optimization/`), и обоснование подхода.

## 1. Данные

| Обозначение | Смысл | Источник (`spec/api_spec.yaml`) |
|---|---|---|
| `O` | наряды дня; для `o ∈ O`: дом `b(o)`, тип `w(o)`, технология, `requires_height`, слот `[a_o, e_o]` (окно **начала** визита: `e_o = latest_start`), срок `D_o`, АО `q_o ∈ ℕ³`, вес `ω_o = 2` для повторных, иначе 1, момент регистрации `r_o`, узел доступа `n(o)` | `PUT /days`, `NEW_ORDER` |
| `K` | сотрудники; для `k`: СЦ `h_k`, профили, технологии, допуск к высоте, смена `[S_k, E_k]`, окно начала перерыва `[β⁻_k, β⁺_k]`, длительность перерыва `π_k`, стартовый запас `Q⁰_k` и вместимость `Q̄_k` | `PUT /reference` |
| `C` | сервисные центры: часы работы, длительность пополнения `ρ_c` | `PUT /reference` |
| `τ(i, j)` | время в пути по **единой матрице** организаторов (решение D2); `τ(i, i) = 0` | `PUT /reference/travel-matrix` |
| `d_w` | норматив работ типа `w` | справочник типов работ |
| `t` | модельное время: `now` дня, затем `timestamp` последнего события | события |

## 2. Решение

Для каждого сотрудника `k` — маршрут: последовательность остановок
`DEPOT_START(h_k) → … → DEPOT_END(h_k)`, где остановка — `VISIT(o)`, `BREAK`, `RESTOCK(c)`;
у каждой остановки `arrival ≤ start ≤ end`. Каждый наряд попадает ровно в одно множество:
маршрут, `unassigned` (с причиной и предложением), `pgp_groups` (передан в станционное
подразделение) или `cancelled`.

Переменные: `x_ok ∈ {0,1}` — наряд `o` у сотрудника `k`; порядок остановок; время начала `s_o`;
место и время перерыва; набор пополнений `RESTOCK`.

## 3. Жёсткие ограничения (H1–H10)

* **H1 допуск**: `x_ok = 1 ⇒` профиль `k` ∩ профили `w(o)` ≠ ∅, технология `o` ∈ технологиям `k`,
  `requires_height(o) ⇒ height_permit(k)`.
* **H2 смена**: `S_k ≤ DEPOT_START.start`, `DEPOT_END.arrival ≤ E_k`.
* **H3 перерыв**: при наличии визитов ровно один `BREAK`, `β⁻_k ≤ start ≤ β⁺_k`, длительность ≥ `π_k`,
  в точке предыдущей остановки (дорога 0), без пересечений.
* **H4 слот**: `a_o ≤ s_o ≤ e_o`; для `NEW_ORDER` ещё `s_o ≥ r_o`.
* **H5 норматив**: `end − start = d_{w(o)}` (или фактическое окончание из `VISIT_DELAYED` / `ORDER_TRANSFERRED`).
* **H6 дорога**: `arrival_{i+1} ≥ end_i + τ(loc_i, loc_{i+1})`.
* **H7 АО**: остаток `Q_k` после каждого визита `≥ 0`, визит списывает `q_o` в момент начала,
  `RESTOCK` доводит до `Q̄_k`.
* **H8 СЦ**: `RESTOCK` — в открытом СЦ на всём интервале, длительность ≥ `ρ_c`.
* **H9 учёт**: каждый наряд ровно в одном месте.
* **H10 заморозка**: остановки с `start < t` не меняются (кроме `end` по событию), новые — не раньше `t`.

Все ограничения проверяет **один** конструктор расписания — `RouteSimulator` (`simulator.py`);
независимо от него каждую версию плана перепроверяет валидатор-оракул (`validator.py`).

## 4. Целевая функция (лексикографическая)

Наряд успешен, если `a_o ≤ s_o ≤ e_o`, `end_o ≤ D_o` и нет нарушений. Сравнение планов
(`evaluation.compare_plans`) — по убыванию приоритета критериев кейса:

1. `max Σ ω_o · success_o` — взвешенное число успешных нарядов (35 % оценки);
2. `min` число переносов (`RESCHEDULE`);
3. `min Σ τ` — суммарное время в пути (15 %);
4. `min CV(u_k)` — коэффициент вариации загрузки `u_k = (работа + дорога) / (смена − перерыв)` (5 %).

Лексикографический порядок, а не взвешенная сумма: невыполненный наряд нельзя «окупить»
сэкономленными минутами дороги — так устроена и оценка кейса.

## 5. Динамика: события и перепланирование

На событии (`NEW_ORDER`, `ORDER_CANCELLED`, `VISIT_DELAYED`, `ORDER_TRANSFERRED`,
`STAFF_UNAVAILABLE`, `TIME_TICK`) состояние «замораживается» в момент `t` (H10), затем —
**минимальное вмешательство** (D20): пересчёт только затронутых маршрутов, вставка
освободившихся нарядов, локальное улучшение, «якоря» (D32). Ответ ≤ 10 с (у нас ≤ 0.12 с на
400 нарядах). Перед переназначением или снятием наряда — `LATE_RISK` (раннее предупреждение,
своевременно — за ≥ 30 мин до слота); прогноз опоздания — `risk.forecast_route` по текущей
последовательности (с историей длительностей, D39).

## 6. ПГП

`pgp_relevant`-наряды (неисправности, деградации) с одного узла доступа: ≥ 3 за скользящее окно
60 мин, размах группы ≤ окна (`pgp.py`). Группа не планируется к выезду, наряды передаются в
станционное подразделение (`TRANSFER_TO_STATION`), алерт `PGP_DETECTED`; `detected_at` не
меняется при пополнении группы; начатые визиты остаются в маршруте.

## 7. Метод и обоснование

| Этап | Метод | Почему |
|---|---|---|
| Начальный план | **regret-3 вставка** (сначала наряды, у которых меньше всего хороших мест) | за секунды даёт допустимый план на 400 нарядов × 40 сотрудников (вместе с LS ≈ 2 с), хорошо работает с узкими окнами |
| Улучшение | **Local Search** (перестановки внутри и между маршрутами, вставка нераспределённых) + **ALNS** (4 оператора разрушения × 2 восстановления, адаптивные веса, отжиг) | стандарт де-факто для VRPTW; anytime — использует любой бюджет до 300 с и останавливается по времени |
| События | ремонт затронутых маршрутов + вставка + LS в пределах бюджета | 10 с на ответ, нельзя пересчитывать день целиком и «дёргать» всех сотрудников |
| Расписание | один симулятор (H1–H10) + независимый валидатор | все эвристики используют одну и ту же проверку — нет рассинхрона «оптимизатор считает допустимым, валидатор нет» |

**Почему не MILP / CP-SAT (OR-Tools).** (1) Ограничения кейса неудобны для готовых решателей:
перерыв в точке предыдущей остановки, рюкзак с пополнением в любом открытом СЦ, заморозка,
нормативы с фактическими окончаниями — их пришлось бы моделировать обходными путями.
(2) На 400 нарядах точная модель не даёт гарантии за 10 с на событие. (3) Лексикографическая
цель и минимальное вмешательство естественно выражаются в эвристике сравнением планов.
Проверка качества — сравнение трёх вариантов на одинаковых днях (`benchmarks/compare.py`):
Full (ALNS) 0.570 · Basic (regret + LS) 0.528 · Baseline (жадный ближайший) 0.431 доли успешных
нарядов, в пути 58 / 67 / 102 ч, 0 нарушений по вине алгоритма (СИНТЕТИКА, `docs/ADO_TASKS.md`).

**Сложность.** Вставка — `O(|O| · |K| · L)` проверок позиций (`L` — длина маршрута) с
отсечениями по нижним оценкам; одна симуляция маршрута — `O(L)`.
